Protocol primer

What is x402?

x402 is an open, transport-agnostic internet payment standard. Version 2 separates core payment types and logic from their representation over transports such as HTTP, MCP and A2A.

Request

A client or agent requests a protected resource.

Requirements

The resource server signals payment requirements, including acceptable scheme, network, amount, asset and destination.

Payload

The client selects an accepted option and creates the appropriate signed payment payload.

Retry

The client retries through the transport with payment information attached.

Verify & settle

The resource server verifies locally or through a facilitator and follows the selected scheme's settlement flow.

Return resource

After successful processing, the protected result and settlement response can be returned.

Protocol language follows the official x402 v2 specification at the inspected commit. x402-XEC currently uses v1-era shapes; this site does not present them as v2-compatible yet.

Research substrate

Why XEC?

The research question is practical: how can native UTXO money participate in machine-readable payment workflows while keeping authorization, policy and custody boundaries explicit?

01

Native UTXO money

XEC provides a direct transaction model for studying exact-value, on-chain settlement without introducing a synthetic application balance.

02

Small-value economics

eCash is relevant to micropayment-style experiments where the cost and operational shape of small transfers matter. No performance number is assumed here.

03

Read and verify

Chronik supplies indexing and read interfaces for controlled UTXO discovery, transaction inspection and eventual confirmation evidence.

04

Wallet boundary

Tonalli is the intended user-agent boundary: exact details are displayed, approval is explicit, and key material remains wallet-owned.

05

Policy before money

The CAE and Agentic Contract V1 model intent, policy, human approval, signing, broadcast and confirmation as separate states.

06

Machine-native workflows

HTTP, paid APIs and later MCP/A2A adapters provide a path to investigate commerce between software agents without pretending it is live today.

No invented dates

Evidence-driven roadmap

The ordering follows dependency and safety boundaries: modernize the protocol contract first, then prove signing and controlled settlement before adding paid services or agent transports.

A

Protocol modernization

  • Compare x402-XEC with current x402 v2.
  • Migrate wire semantics where required.
  • Establish a standardized XEC network identifier and document the (scheme, network) pair.
  • Update compatibility and security tests.
B

Tonalli execution boundary

  • Preserve explicit approval.
  • Add real prepared-transaction signing inside Tonalli.
  • Keep wallet secrets outside x402-XEC.
  • Bind invoice, resource, amount and payTo exactly.
C

Controlled XEC E2E

  • Read-only UTXO discovery and deterministic plan.
  • Tiny controlled value with explicit approval.
  • Exact signing and separately authorized broadcast.
  • Chronik verification, confirmation and reproducible evidence.
D

First paid API

  • Create a real x402-protected resource using XEC.
  • Deploy the settlement backend separately.
  • Keep this GitHub Pages portal honest about its static role.
E

Agent payments

  • Connect AgentIntentV1 to CAE.
  • Bind x402 requirements to Tonalli policy and approval.
  • Deliver the protected resource only after verified payment state.
F

MCP / A2A

  • Track current upstream transport specifications.
  • Build adapters only after the v2 XEC scheme is stable.
  • Preserve the same policy and custody boundaries across transports.
G

Discovery

  • Explore Bazaar metadata for XEC-paid resources.
  • Validate catalog claims against live evidence.
  • Publish no discoverable endpoint before the paid API exists.
