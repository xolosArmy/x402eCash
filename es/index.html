Introducción al protocolo

¿Qué es x402?

x402 es un estándar abierto y agnóstico al transporte para pagos nativos de internet. La versión 2 separa los tipos y la lógica centrales del pago de su representación en transportes como HTTP, MCP y A2A.

Solicitud

Un cliente o agente solicita un recurso protegido.

Requisitos

El servidor comunica los requisitos de pago: esquema, red, monto, activo y destino aceptados.

Payload

El cliente selecciona una opción aceptada y crea el payload de pago firmado correspondiente.

Reintento

El cliente repite la solicitud mediante el transporte con la información del pago adjunta.

Verificación y liquidación

El servidor verifica localmente o mediante un facilitador y sigue el flujo de liquidación del esquema elegido.

Entrega del recurso

Tras procesar el pago correctamente, puede devolver el resultado protegido y la respuesta de liquidación.

La terminología sigue la especificación oficial x402 v2 en el commit inspeccionado. x402-XEC todavía usa estructuras de la época de v1; este sitio no las presenta aún como compatibles con v2.

Base de investigación

¿Por qué XEC?

La pregunta de investigación es práctica: ¿cómo puede el dinero UTXO nativo participar en flujos de pago legibles por máquinas manteniendo explícitos los límites de autorización, política y custodia?

01

Dinero UTXO nativo

XEC ofrece un modelo directo de transacciones para estudiar liquidación on-chain de valor exacto sin introducir un saldo sintético de aplicación.

02

Economía de valores pequeños

eCash es relevante para experimentos similares a micropagos, donde importan el costo y la forma operativa de transferencias pequeñas. Aquí no suponemos cifras de rendimiento.

03

Lectura y verificación

Chronik brinda interfaces de indexación y lectura para descubrir UTXOs, inspeccionar transacciones y producir futura evidencia de confirmación.

04

Límite de la wallet

Tonalli es el límite previsto para usuario y agente: muestra los datos exactos, exige aprobación explícita y conserva las llaves dentro de la wallet.

05

Política antes del dinero

CAE y Agentic Contract V1 modelan por separado intención, política, aprobación humana, firma, broadcast y confirmación.

06

Flujos nativos para máquinas

HTTP, las APIs cobrables y, más adelante, los adaptadores MCP/A2A permiten investigar comercio entre agentes sin fingir que hoy está activo.

CAE / Tonalli Agents

Están implementados decisiones fail-closed, kill switch, allowlists de destino, límites diarios acumulados y controles anti-replay. Incluso una política aprobada se detiene antes de firma y broadcast.

Sin fechas inventadas

Ruta guiada por evidencia

El orden sigue dependencias y límites de seguridad: primero modernizar el contrato del protocolo; después demostrar firma y liquidación controlada; por último, añadir servicios cobrables y transportes para agentes.

A

Modernización del protocolo

  • Comparar x402-XEC con x402 v2 actual.
  • Migrar semántica de wire cuando corresponda.
  • Establecer un identificador XEC normalizado y documentar el par (scheme, network).
  • Actualizar pruebas de compatibilidad y seguridad.
B

Límite de ejecución Tonalli

  • Conservar la aprobación explícita.
  • Añadir firma de transacción preparada dentro de Tonalli.
  • Mantener secretos fuera de x402-XEC.
  • Vincular exactamente factura, recurso, monto y payTo.
C

E2E XEC controlado

  • Descubrimiento read-only de UTXOs y plan determinista.
  • Valor mínimo controlado y aprobación explícita.
  • Firma exacta y broadcast autorizado por separado.
  • Verificación Chronik, confirmación y evidencia reproducible.
D

Primera API cobrable

  • Crear un recurso x402 real protegido con XEC.
  • Desplegar por separado el backend de liquidación.
  • Mantener honesto este portal estático en GitHub Pages.
E

Pagos entre agentes

  • Conectar AgentIntentV1 con CAE.
  • Vincular requisitos x402 con política y aprobación Tonalli.
  • Entregar el recurso protegido solo tras verificar el estado del pago.
F

MCP / A2A

  • Seguir las especificaciones upstream vigentes.
  • Construir adaptadores solo después de estabilizar el esquema XEC v2.
  • Conservar los mismos límites de política y custodia en cada transporte.
G

Descubrimiento

  • Explorar metadata Bazaar para recursos cobrables en XEC.
  • Validar el catálogo contra evidencia real.
  • No publicar endpoints descubribles antes de que exista la API cobrable.
